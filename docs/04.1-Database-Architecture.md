# Purpose

This document defines the logical and physical database architecture of Atlas.

The Atlas database is designed to preserve infrastructure knowledge over time rather than simply storing operational data. It supports authentication, domain ownership, asynchronous Understanding execution, immutable historical snapshots, and future Infrastructure Intelligence capabilities.

The database forms the historical memory of Atlas.

---

# Database Philosophy

Atlas follows several core database principles.

## Immutable Infrastructure History

Infrastructure observations are never updated after creation.

Each Understanding execution produces a new Infrastructure Snapshot.

Historical observations remain permanently available for future comparison and intelligence generation.

---

## Multi-Tenant Isolation

Every business resource belongs to a user through domain ownership.

```
User
    │
    ▼
Domain
    │
    ▼
Understanding Jobs
    │
    ▼
Infrastructure Snapshots
```

Tenant isolation is enforced through foreign-key relationships and application-level authorization.

---

## Intelligence-First Storage

The database is designed to support infrastructure intelligence rather than temporary scan results.

Infrastructure data progresses through an intelligence pipeline:

```
Infrastructure Snapshot
        │
        ▼
Infrastructure Findings
        │
        ▼
Change History
        │
        ▼
Infrastructure Brief
```

This model enables Atlas to understand infrastructure evolution across time.

Each user owns one or more infrastructure domains.

# Domain

## Purpose

Represents an infrastructure asset managed by Atlas.

Every Understanding execution is associated with exactly one domain.

Domains form the root aggregate for infrastructure intelligence.

---

## Responsibilities

- Infrastructure ownership
- Multi-tenant isolation
- Historical infrastructure grouping
- Monitoring configuration

---

## Relationships

```
Domain
 ├── User (N:1)
 ├── UnderstandingJobs (1:N)
 ├── InfrastructureSnapshots (1:N)
 └── ChangeHistory (1:N)
```

---

## Key Fields

| Field | Description |
|-------|-------------|
| id | UUID primary key |
| userId | Domain owner |
| domainName | Fully qualified domain name |
| monitoringEnabled | Enables future scheduled monitoring |
| createdAt | Domain creation time |
| updatedAt | Last modification timestamp |

Each user may register the same domain only once.

The composite unique constraint:

```

```

# Infrastructure Snapshot

## Purpose

Infrastructure Snapshots represent the immutable historical memory of Atlas.

Each successful Understanding execution produces exactly one Infrastructure Snapshot containing the complete observed infrastructure state at a specific point in time.

Snapshots are never modified after creation.

---

## Responsibilities

- Preserve infrastructure history
- Store canonical discovery payload
- Record response metadata
- Associate observations with Understanding Jobs
- Serve as the foundation for future intelligence generation

---

## Relationships

```
InfrastructureSnapshot
├── Domain (N:1)
├── UnderstandingJob (1:1)
├── InfrastructureFinding (1:N)
├── InfrastructureBrief (1:1)
├── Previous Changes (1:N)
└── Current Changes (1:N)
```

---

## Key Fields

| Field | Description |
|-------|-------------|
| id | UUID primary key |
| domainId | Associated domain |
| jobId | Understanding Job |
| responseTimeMs | Total HTTP response time |
| httpStatus | Primary HTTP status |
| payload | Canonical discovery payload |
| createdAt | Snapshot timestamp |

## Canonical Payload

Rather than distributing infrastructure observations across numerous relational tables, Atlas stores the complete discovery output as a canonical JSON document.

The payload contains information collected by all discovery modules.

Example structure:

```text
payload
├── dns
├── http
├── ssl
├── technology
└── metadata
```

This approach provides:

- Schema flexibility
- Efficient persistence
- Historical fidelity
- Forward compatibility

The JSON payload represents the source of truth for a completed Understanding execution.

# Referential Integrity

All business entities are connected through explicit foreign-key relationships.

Cascade deletion is applied where dependent records should not outlive their parent resource.

Examples:

```
User
    │
    ▼
Domain
    │
    ▼
Understanding Job
    │
    ▼
Infrastructure Snapshot
```

This guarantees database consistency while simplifying lifecycle management.

---

# Database Constraints

Atlas uses database constraints to preserve data integrity and enforce business rules at the persistence layer.

---

## Primary Keys

Every entity uses a UUID primary key.

Benefits include:

- Globally unique identifiers
- Simplified distributed systems
- Reduced enumeration risk
- Stable external references

---

## Foreign Keys

Relationships are enforced using foreign-key constraints.

Examples include:

```
Domain
    │
    ▼
User

UnderstandingJob
    │
    ▼
Domain

InfrastructureSnapshot
    │
    ▼
UnderstandingJob
```

Foreign keys ensure that orphaned business records cannot exist.

---

## Unique Constraints

Atlas defines unique constraints where required by business rules.

Examples:

### User

```
email
```

Guarantees one account per email address.

---

### Domain

```
(userId, domainName)
```

Prevents duplicate domain registrations for the same user while allowing different users to analyze the same public infrastructure independently.

---

### Infrastructure Snapshot

```
jobId
```

Guarantees that each Understanding Job produces at most one Infrastructure Snapshot.

---

### Infrastructure Brief

```
snapshotId
```

Guarantees a single Infrastructure Brief for each Infrastructure Snapshot.

# Performance Strategy

The database is optimized for Atlas' primary access patterns.

## Read Optimization

Frequent read operations include:

- User authentication
- Domain retrieval
- Understanding Job history
- Infrastructure Snapshot history
- Future Finding retrieval
- Future Change History timeline

Indexes are created to support these queries efficiently.

---

## Write Optimization

Infrastructure discovery is append-only.

Most writes consist of:

- New Understanding Jobs
- New Infrastructure Snapshots
- Future Findings
- Future Change History
- Future Infrastructure Briefs

Atlas avoids modifying historical records after creation.

---

## JSON Storage

Infrastructure observations are stored as structured JSON within the Infrastructure Snapshot.

Advantages include:

- Flexible schema evolution
- Preservation of complete discovery output
- Reduced schema complexity
- Efficient historical storage

Normalized entities such as Findings and Change History are derived from this canonical payload rather than replacing it.

---

# Scalability Considerations

The schema is designed to scale through incremental growth rather than architectural redesign.

Future enhancements may include:

- Read replicas
- Table partitioning
- Snapshot archival
- Historical data retention policies
- Background data maintenance
- Query optimization

The current schema provides a stable foundation for these enhancements without requiring changes to the domain model.

---

# Backup and Recovery

Infrastructure history represents one of Atlas' most valuable assets.

Production deployments should include:

- Automated database backups
- Point-in-time recovery
- Periodic restore validation
- Off-site backup storage
- Backup monitoring

Because Infrastructure Snapshots are immutable, backup consistency is simplified and historical integrity is preserved.

# Summary

The Atlas database is designed as a historical knowledge store rather than a temporary operational datastore.

Sprint 2 establishes the production persistence layer with authenticated users, domain ownership, asynchronous Understanding Jobs, and immutable Infrastructure Snapshots.

Future releases build upon this foundation by generating Infrastructure Findings, tracking historical changes, and producing human-readable Infrastructure Briefs without altering the underlying historical record.

The result is a database architecture that preserves infrastructure history while enabling Atlas to evolve into a complete Infrastructure Intelligence Platform.
