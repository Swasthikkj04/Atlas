# Purpose

This document defines the production database architecture of Atlas.

While **04-Databases.md** explains the logical data model, this document specifies how Atlas stores, protects, manages, and scales data in a production environment.

The database is not merely a storage layer.

It is Atlas' long-term memory.

Every design decision in this document must reinforce Atlas' mission:

> **Know what changed. Understand why.**

---

# Architecture Philosophy

Atlas is built on four principles.

## 1. Security by Design

Security is a foundational requirement rather than an optional feature.

The database must minimize attack surfaces, protect user information, and enforce strict ownership boundaries.

---

## 2. Privacy by Design

Atlas stores only the information required to deliver value.

The platform intentionally avoids collecting unnecessary personal information.

Trust is earned through restraint.

---

## 3. Trust by Design

Users should always understand what Atlas remembers.

Guest users remain anonymous.

Persistence begins only after a user explicitly asks Atlas to remember their infrastructure.

---

## 4. History by Design

Atlas does not overwrite understanding.

Every understanding creates historical knowledge.

History is preserved.

Understanding grows over time.

The database must:

- Secure user accounts
- Preserve historical infrastructure knowledge
- Enable infrastructure comparison
- Support future scalability
- Enable multi-tenancy
- Protect user privacy
- Remain modular
- Support future infrastructure modules

# Security Principles

Atlas follows a defense-in-depth strategy.

## Password Storage

Passwords are never stored.

Only secure password hashes are persisted.

Recommended algorithm:

- Argon2id

Future password upgrades must not require schema redesign.

---

## Authentication

Authentication data is isolated from infrastructure data.

JWTs, sessions, OTPs, and temporary verification tokens are not stored in the primary user table.

---

## Least Privilege

Every database query must be scoped to the authenticated user.

Example

User A must never be capable of retrieving:

- User B domains
- User B snapshots
- User B briefs
- User B infrastructure history

---

## Public Infrastructure

Infrastructure data represents publicly available website information.

Ownership applies only to Atlas' historical understanding.

---

# Privacy Principles

Atlas intentionally minimizes data collection.

Version 1 stores only:

- Full name
- Email
- Password hash

Atlas intentionally does not collect:

- Phone number
- Address
- Date of birth
- Government identifiers
- Payment information
- Social profiles

Additional data should only be introduced when a genuine product requirement exists.

---
## Ownership Architecture

Atlas follows a strict ownership model.

Every persistent record must have exactly one logical owner.

Ownership is inherited through relationships rather than duplicated.

```text
User
 └── Domain
      ├── UnderstandingJob
      ├── InfrastructureSnapshot
      │      ├── InfrastructureFinding
      │      └── InfrastructureBrief
      └── ChangeHistory
```

This architecture provides:

* Strong tenant isolation
* Simple authorization
* Predictable cascading behaviour
* Clear ownership boundaries
* Future multi-tenant scalability

No business entity should exist without an identifiable ownership chain.


# Guest Mode Architecture

Guest users may understand any public website without creating an account.

Guest understanding is temporary.

Guest sessions are **not persisted** in PostgreSQL.

Guest data exists only for the duration of the request and is discarded immediately after completion.

Persistent history begins only after the user creates an account and chooses to let Atlas remember their infrastructure.

This reinforces Atlas' philosophy:

> Earn trust before asking for commitment.

---

# Multi-Tenant Architecture

Atlas is designed as a multi-tenant SaaS platform.

Every authenticated user owns an isolated dataset.

Users may watch identical public domains.

Example

User A

└── github.com

User B

└── github.com

Both users maintain completely independent historical timelines.

No tenant can access another tenant's information.

Future support for organizations and teams should not require redesigning existing tables.

## Infrastructure Brief Architecture

Infrastructure Briefs are generated from Infrastructure Snapshots.

Each completed Infrastructure Snapshot produces exactly one Infrastructure Brief.

Relationship:

```text
InfrastructureSnapshot
        │
        ▼
InfrastructureBrief
```

This one-to-one relationship ensures that every historical observation has a corresponding human-readable explanation.

Infrastructure Briefs are immutable historical artifacts and form part of Atlas' permanent understanding of infrastructure evolution.

Future versions may support multiple presentation formats generated from the same historical snapshot without modifying the original brief.


# UUID Strategy

Atlas uses UUIDs as primary identifiers.

Reasons:

- Prevent predictable identifiers
- Improve API security
- Support distributed systems
- Simplify future horizontal scaling

Sequential IDs are intentionally avoided.

# Data Integrity Rules

Atlas enforces the following invariants.

- Email addresses are unique.
- A user cannot watch the same domain twice.
- Multiple users may watch the same domain.
- Every snapshot belongs to exactly one domain.
- Every finding belongs to exactly one snapshot.
- Every change references two snapshots.
- Infrastructure briefs belong to one user.
- Historical snapshots are immutable.

---

# Indexing Strategy

Primary indexes:

- User ID
- Domain ID
- Snapshot ID
- Created At

Additional indexes:

- Email
- Domain Name
- User + Domain composite
- Job Status
- Snapshot Creation Time

Indexes may evolve based on production telemetry.

---

# Scalability Strategy

Atlas follows a Modular Monolith architecture during Version 1.

The database must support future extraction into independent services without redesign.

Future services may include:

- Scan Manager
- Comparison Engine
- Notification Service
- AI Understanding
- Team Workspace

The database schema should remain stable throughout this evolution.

# Prisma Implementation Standards

Every Prisma model should follow these conventions.

- UUID primary keys
- `createdAt` on all models
- `updatedAt` only on mutable models
- Foreign key indexes
- Composite unique constraints where appropriate
- Enum usage instead of free-form status strings
- Explicit relation names
- Cascade behavior defined intentionally

The Prisma schema is an implementation of this document—not the source of architectural decisions.
