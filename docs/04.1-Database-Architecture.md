# Database Philosophy

Atlas is not designed to store websites.

Atlas is designed to build knowledge.

Traditional monitoring platforms continuously overwrite the current state of infrastructure.

Atlas continuously understands infrastructure, preserves historical observations, compares them over time, and explains meaningful changes.

Every understanding contributes to Atlas' long-term knowledge.

The database is therefore the permanent memory of the platform.

---

# Architecture Principles

Every database decision within Atlas must satisfy these principles.

## Documentation First

Architecture is documented before implementation.

Database schemas, migrations, and code must implement approved documentation rather than define it.

---

## Security by Design

Security is designed before implementation.

Ownership, authorization, and tenant isolation are architectural concerns—not implementation details.

---

## Trust by Design

Atlas earns persistence rather than forcing it.

Guest users may understand infrastructure immediately.

Persistent storage begins only after a user explicitly chooses to let Atlas remember their infrastructure.

---

## Historical Truth Is Immutable

Historical observations are append-only.

Atlas never rewrites historical knowledge.

Corrections or improved understanding generate new records rather than modifying existing ones.

---

## Tenant Isolation

Every persistent record belongs to exactly one tenant through a well-defined ownership hierarchy.

One user's infrastructure must never be visible to another user.

This requirement applies to every layer of the application.

Infrastructure knowledge moves through a predictable lifecycle.

```text

↓

Understand

↓

No Persistence

────────────────────────────

Registered User

↓

Understanding Job

↓

Infrastructure Snapshot

↓

Infrastructure Findings

↓

Comparison Engine

↓

Change History

↓

Infrastructure Brief

↓

Historical Timeline
```

Guest sessions remain temporary.

Registered users continuously build historical knowledge.

---

# Ownership Architecture

Atlas follows a strict ownership hierarchy.

Every persistent business entity has one logical owner.

Ownership is inherited through relationships rather than duplicated.

```text
User
 └── Domain
      ├── UnderstandingJob
      ├── InfrastructureSnapshot
      │      ├── InfrastructureFinding
      │      └── InfrastructureBrief
      └── ChangeHistory
```

Benefits include:

* Strong tenant isolation
* Simplified authorization
* Reduced redundancy
* Predictable cascading behaviour
* Clear auditability

No business entity should exist without an identifiable ownership chain.

---

# Mutable vs Immutable Data

Atlas distinguishes between operational configuration and historical knowledge.

## Mutable Operational Data

These models represent current system configuration.

Examples:

* User
* Domain

These records may be updated throughout their lifecycle.

---

## Lifecycle Data

Some entities naturally progress through execution states.

Example:

* UnderstandingJob

A job may transition from:

```text
PENDING

↓

RUNNING

↓

COMPLETED

or

FAILED
```

After reaching a terminal state, the job should not be modified except for exceptional operational maintenance.

---

## Immutable Historical Data

The following entities are permanent historical records:

* InfrastructureSnapshot
* InfrastructureFinding
* ChangeHistory
* InfrastructureBrief

These entities are append-only.

Atlas preserves history rather than replacing it.

# Historical Architecture

Historical understanding is the foundation of Atlas.

Every completed understanding produces a permanent historical record.

```text
Understanding

↓

Snapshot

↓

Comparison

↓

History

↓

Infrastructure Brief

↓

Timeline
```

This architecture enables:

* Infrastructure evolution
* Historical comparison
* Regression detection
* AI-assisted understanding
* Long-term trend analysis

---

# Multi-Tenant Architecture

Atlas is a production-grade multi-tenant SaaS platform.

Every query must execute within the authenticated user's ownership boundary.

Authorization follows the ownership hierarchy.

Conceptually:

```text
Authenticated User

↓

Owned Domain

↓

Owned Historical Data
```

Tenant isolation must never depend on frontend validation alone.

The backend is the authoritative enforcement point.

---

# Performance Strategy

Atlas is designed primarily for read-heavy workloads.

Users frequently:

* View timelines
* Read Infrastructure Briefs
* Compare historical understandings
* Browse findings

Historical records are written once and read many times.

Database optimization therefore prioritizes efficient historical retrieval.

Indexes should support:

* Ownership
* Domain history
* Snapshot retrieval
* Timeline generation

Future optimizations may include:

* Partitioning
* Materialized views
* Read replicas
* Archival strategies

without changing the logical domain model.

---

# Data Integrity

The following architectural rules must always remain true.

* Every persistent record has one logical owner.
* Every Understanding Job belongs to one Domain.
* Every Infrastructure Snapshot belongs to one Understanding Job.
* Every Infrastructure Finding belongs to one Infrastructure Snapshot.
* Every Infrastructure Brief belongs to one Infrastructure Snapshot.
* Every Change History entry belongs to one Domain.
* Historical observations are never modified.
* Guest understanding is never persisted.

These rules are architectural invariants.

Future implementations must preserve them.

---

# Security Architecture

Database security follows the principles defined in the Security & Trust Architecture.

Core protections include:

* UUID primary keys
* Foreign key integrity
* Ownership-aware queries
* Immutable historical records
* Tenant isolation
* Defense in depth

Future enhancements may include:

* PostgreSQL Row-Level Security (RLS)
* Audit logging
* Encryption enhancements
* Data retention policies

without requiring changes to the core domain model.

---

# Scalability Strategy

Atlas is designed to scale through architectural evolution rather than schema redesign.

Future improvements may include:

* Background processing
* Distributed scan workers
* Event-driven processing
* Horizontal database scaling
* Read replicas
* Historical data archiving

The Version 1 domain model is intentionally designed to support these future capabilities without requiring fundamental structural changes.

---

# Database Invariants

The following statements must always remain true.

1. Every persistent record has one owner.
2. One user must never access another user's data.
3. Guest understanding is never persisted.
4. Historical truth is immutable.
5. Every understanding creates a new historical record.
6. Infrastructure Briefs belong to Infrastructure Snapshots.
7. Documentation precedes implementation.

Any future design that violates these invariants should be reconsidered.

---

# Version 1 Freeze

The Atlas Version 1 database architecture is considered stable.

Future modifications require:

1. Product justification
2. Architecture review
3. Documentation update
4. Implementation

This ensures that architectural decisions remain intentional and documented.

---

# Summary

The Atlas database is more than a persistence layer.

It is the product's long-term memory.

Every understanding strengthens Atlas' knowledge.

Every snapshot preserves history.

Every comparison creates insight.

Every Infrastructure Brief transforms technical observations into human understanding.

By protecting historical truth, enforcing tenant isolation, and prioritizing documentation-first engineering, the Atlas database provides a production-ready foundation capable of supporting the platform's long-term evolution without compromising trust, security, or maintainability.
